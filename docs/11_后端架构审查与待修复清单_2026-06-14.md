# 后端架构审查与待修复清单

日期：2026-06-14  
范围：`backend` 目录当前 `dev` 分支实现  
结论状态：仅记录问题与建议，不执行本轮修复

## 1. 审查结论

当前后端整体分层方向基本合理，已经具备：

- `api -> services -> domain/repositories/db` 的主分层
- 复杂 SQL 相关的独立服务拆分
- 图模型、血缘模型、元数据模型等基础抽象

但现阶段的主要风险已经从“缺少能力”转为“边界开始变形”，重点体现在：

1. 控制器承担了过多编排职责。
2. 元数据标识口径不统一。
3. 多个服务间出现重复实现和重复工具函数。
4. 仓库内开始混入遗留代码、空实现和运行噪音。

这类问题短期不会让系统立刻不可用，但会明显提高后续复杂 SQL 能力继续迭代时的维护成本和回归风险。

## 2. 优先级总表

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 元数据仓储按 `table_name` 查询，与上游全限定表名口径不一致 | 影响元数据命中、列解析、`*` 展开和同名表场景 |
| P1 | `analyze_controller` 过重，控制器内混合主流程编排、图组装、结果组装和策略逻辑 | 后续改造容易继续堆逻辑，测试边界不清 |
| P2 | 多处重复工具函数和重复 SQL 树遍历逻辑 | 修一处漏一处，行为逐步漂移 |
| P2 | 启动时执行迁移存在导入副作用 | 测试、脚本、worker 启动边界不清晰 |
| P2 | API 模型与 Domain 图模型存在双套表示 | 增加转换成本，容易出现契约漂移 |
| P3 | 存在遗留函数、空实现、调试脚本和乱码注释 | 增加理解成本，污染后续扫描结果 |
| P3 | 运行日志和打包目录混入仓库工作区 | 干扰提交、review 和后续排查 |

## 3. 详细问题

### 3.1 P1 元数据标识口径不统一

现状：

- 上游结构分析输出的是带 `catalog/schema/table` 的完整表名。
- 位置证据：
  - `backend/app/services/query_structure_service.py:48`
  - `backend/app/services/query_structure_service.py:111`
  - `backend/app/api/analyze_controller.py:444`
- 但仓储层查询只按 `tm.table_name` 过滤。
- 位置证据：
  - `backend/app/repositories/metadata_repository.py:81`
  - `backend/app/repositories/metadata_repository.py:97`

风险：

- 当 SQL 使用全限定表名时，元数据可能查不到。
- 当不同 schema 下存在同名表时，结果可能错配。
- 会直接影响后续复杂 SQL 场景中的列解析、星号展开和置信度判断。

建议修复方向：

- 统一元数据主键口径，至少在仓储层显式支持 `catalog + schema + table_name`。
- 保留旧接口兼容层，但主分析链路不要继续依赖裸 `table_name`。
- 增加全限定表名和跨 schema 同名表测试。

### 3.2 P1 `analyze_controller` 过重

现状：

- 主控制器已经不只是 HTTP 入口，而是同时负责：
  - parse 后分支路由
  - recovery fallback
  - structure/context 构造
  - lineage 调度
  - graph 合并
  - source location 调度
  - capability 拼装
  - confidence 调整
  - result DTO 组装
- 位置证据：
  - `backend/app/api/analyze_controller.py:36`
  - `backend/app/api/analyze_controller.py:297`
  - `backend/app/api/analyze_controller.py:337`
  - `backend/app/api/analyze_controller.py:405`
  - `backend/app/api/analyze_controller.py:488`

风险：

- 每增加一轮复杂 SQL 能力，控制器还会继续膨胀。
- 控制器层很难做稳定单测，容易退化为“只能靠集成测试兜底”。
- 主链路改动时，结果组装与策略逻辑容易被误伤。

建议修复方向：

- 抽出统一的 analysis orchestrator 或 application service。
- 控制器只保留 request/response 转换和异常边界。
- `_assemble_result`、`_adjust_confidence`、graph build 协调等逻辑应逐步下沉。

### 3.3 P2 重复工具函数和重复逻辑已经出现

现状：

- `_table_name_without_alias` 至少有 3 份：
  - `backend/app/services/table_structure_service.py:127`
  - `backend/app/services/cte_structure_service.py:161`
  - `backend/app/services/name_resolver.py:387`
- `_dedupe_diagnostics` 至少有 3 份：
  - `backend/app/services/sql_parse_service.py:132`
  - `backend/app/api/analyze_controller.py:488`
  - `backend/app/complex_sql_guard/analyzer.py:470`

风险：

- 后续如果某一处修复大小写、引号、别名或诊断去重策略，其他地方可能不会同步。
- 同一 SQL 在不同分支里可能得到不同口径的表名或诊断结果。

建议修复方向：

- 将公共标识规范化、表名提取、诊断去重下沉到共享模块。
- 对 SQL 树遍历类公共逻辑先做最小收敛，不要一次性大重构。

### 3.4 P2 启动时执行迁移有导入副作用

现状：

- `backend/app/main.py:12` 在模块加载时直接执行 `run_migrations()`。
- 迁移逻辑位于 `backend/app/db/sqlite.py:18`。

风险：

- 测试导入应用模块时会隐式执行迁移。
- 后续如果引入多 worker 或更多脚本入口，启动副作用会变得更难控制。

建议修复方向：

- 将迁移放到显式启动阶段或独立脚本。
- 至少保证“导入模块”和“执行应用启动动作”分离。

### 3.5 P2 API 模型与 Domain 模型存在双套图表示

现状：

- API 层使用 `backend/app/models.py` 中的 `GraphViewModel`。
- Domain 层使用 `backend/app/domain/graph_view_model.py` 中的 `GraphModel/GraphNode/GraphEdge`。
- 当前 `analyze_controller` 中存在多次 `GraphModel -> dict -> GraphViewModel` 的转换。
- 位置证据：
  - `backend/app/models.py:82`
  - `backend/app/models.py:123`
  - `backend/app/domain/graph_view_model.py:65`
  - `backend/app/api/analyze_controller.py:77`
  - `backend/app/api/analyze_controller.py:225`

风险：

- 图字段新增或修改时，需要同时维护两层结构。
- 若没有契约测试，容易出现 API 返回与内部图模型不一致。

建议修复方向：

- 保留 API DTO 是合理的，但需要明确“唯一内部图模型”。
- 统一转换出口，避免在多个地方临时 `to_dict()` 再二次构造。

## 4. 测试盲区

当前测试覆盖还存在以下空白：

1. 仓储测试只验证了裸 `table_name` 查询，没有验证全限定表名。
   - `backend/tests/test_metadata_repository.py:45`
   - `backend/tests/test_metadata_repository.py:53`
2. 缺少跨 schema 同名表元数据命中测试。
3. 缺少 controller 编排层的更细粒度测试，目前更偏向集成验证。
4. 对遗留函数、未使用私有函数没有清理约束，容易长期残留。

## 5. 建议修复顺序

建议按以下顺序推进，避免改动面过大：

1. 修复元数据标识统一问题。
2. 抽离分析编排层，给 `analyze_controller` 瘦身。
3. 收敛重复工具函数和公共 SQL 标识处理逻辑。
4. 处理启动副作用。
5. 清理遗留函数、调试脚本、乱码注释和运行噪音。
